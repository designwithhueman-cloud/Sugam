# Avara Detector Specification

Version 1.0.0-draft for rule library 1.0.0-draft. Machine-readable source: `src/detectors/detector-specs.json` (checked by `test/detector-spec.mjs`). This document is generated from it.

Each of every rule answers five questions: can it be evaluated automatically, with which detector type, from what data, with what evidence, and what pass, fail and "could not verify" look like.

## Detector types

| Type | What it is |
|---|---|
| DOM | Reads the rendered DOM and computed styles in one page.evaluate. No interaction. Deterministic. |
| Playwright | Drives the page: resize, click, type, press keys, follow links, watch network and timing. Deterministic given the same page. |
| Screenshot Analysis | Compares or inspects screenshots (focus rings, grayscale, saliency, balance). Pixel checks are deterministic; interpretation is advisory. |
| Lighthouse | Mobile Lighthouse run(s) under stated simulated conditions; lab values only. Field data (CrUX) is separate. |
| Axe | axe-core rule results (violations, passes, incomplete), plus Sugam checks that extend it. |
| AI Judgement | A model is handed the rule (id, title, evaluationPrompt) as data and a page-context slice. It must quote evidence that exists in the context. Never confirms a failure alone. |
| Hybrid | Two or more of the above in a fixed order: deterministic extraction or measurement first, judgement only for what remains. |
| None (human session) | Needs a person, a participant or an assistive-technology session. The engine reports it as not run. |
| None (rollup) | A summary of other rules. Zero weight, no independent result. |

## Results every detector can return

| Result | Meaning |
|---|---|
| `observed_pass` | The check ran and the condition holds. |
| `observed_failure` | The check ran and the condition fails, with evidence. |
| `needs_human_review` | A pattern was found that only a person can decide, or a model flagged it. |
| `inconclusive` | The check ran but the evidence cannot decide. |
| `not_applicable` | The rule does not apply to this page. |
| `not_run` | The check could have run but did not (analyzer failed, no AI key, needs a person). |
| `unimplemented` | No detector exists yet. |

**Could not verify.** "Could not verify" is returned whenever the detector did not run, the target was not found, the evidence was ambiguous, or a required input (goal, design system, owner evidence, field data) was not supplied. It is never rounded up to pass and never to fail.

## Evidence record

Every finding stores: ruleId, ruleVersion, url, viewport, inputMode, pageState, element identity (selector + html), expected, observed, measurement or quote, screenshot crop (where visual), detector id + version, timestamp. Raw observations are kept for every tested state.

## Adding or changing a detector

1. Implement the detector so it returns `{ ran, hits[] }` for its id (see `src/services/scan-service`).
2. Add its id to the rule's `evaluator.detectors` in `src/rules/<category>.json`. No engine change.
3. Update the rule's entry in `detector-specs.json` (`implementation` is derived from the rule JSON by the test).
4. Add a passing and a failing fixture, then add the detector id to `exercisedDetectors` in `src/rules/_manifest.json`.
